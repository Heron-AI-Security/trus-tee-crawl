# Performance runs

These runs are the exploratory measurements of October 2026. The paper's results come from the plain / TDX / receipts /
sealed-fleet / WireGuard / custody runs at 1K to 1M, which will be added as separate rows. Gaps in this table ("—") are values
that were not measured in that run; the notes say why.

One row per benchmark run, newest last within each date. Each run id links to a folder with the derived data behind its row:
`summary.json` (every measured value and where it came from), `jobs.csv` (one row per Hadoop job: phase, start, finish, seconds,
YARN CPU), `receipts.json` (receipt and per-URL outcome counts, for runs with receipts) and `hostcpu.json` (whole-cluster CPU from
`/proc`, where it was measured). No raw logs, WARCs, project ids, IP addresses or credentials are kept here; `gen_perf_docs.py`
rebuilds the run folders and the table below (it writes the table to `TABLE.md`, which is pasted under "Runs") from the raw runs.

## Configurations and series

| Config in the run id | What ran |
|---|---|
| `plain` | Common Crawl's Nutch (`commoncrawl/nutch` branch `cc`, commit 3270a761e) on a benchmark cluster, no receipts |
| `receipts` | The same Nutch plus the source-receipt patch, writing WARC files with receipts |
| `custody` | The full fleet: sealed TDX image, WireGuard mesh, encrypted scratch disk, HDFS signing wrapper, receipts and export |

| Series | Meaning |
|---|---|
| `live` | 1 master + 1 worker, live web (the first baselines) |
| `scale` | 1 master + 2 workers, live web, on TDX (`tdx`) or plain (`vm`) c3-standard-4 VMs |
| `replay`, `replay2` | 1 master + 1 worker, recorded web replayed through a proxy, so every run fetches identical pages |
| `2round` | Two crawl rounds; round 2 fetches the links found in round 1 |
| `abc` | Plain, receipts and custody interleaved in three rounds on the same 908 seeds, same day (31 Oct) |
| `prof` | Like `abc`, with async-profiler in every map task (adds CPU; for the breakdown only) |

## Columns

- **seed URLs / fetched:** seeds injected / pages the crawl database marks as fetched.
- **receipts / outcomes / URLs with no outcome:** receipts written; per-URL outcome records (one per scheduled fetch, receipted or not); seeds with no outcome record at all.
- **wall time per phase:** seconds per crawl phase, from the Hadoop job start and finish times; "total" is the crawl script's wall clock.
- **VM-hours / cost:** crawl only (nodes x crawl wall clock), at the c3-standard-4 list price of $0.2016 per hour (us-central1).
  The TDX surcharge is not in Google's price catalog and is not included, nor are disks, idle time or image builds.

## Caveats

- The `abc` custody runs use 908 of the 1K seeds: 92 fail the fleet's seed rule (it rejects query strings and percent-encoding).
  The same 908 were used for plain and receipts.
- In every `abc` receipts and custody run, 12 of the 908 seeds have no outcome record. Not yet explained.
- Custody totals include the fleet's own `readdb -stats` job (~18 s), which the benchmark clusters run outside the crawl script.
- Host CPU exists only where `/proc` snapshots were taken (rounds 2 and 3 of `abc`); custody round 3's was discarded because its
  after-crawl snapshot came 8.5 hours late. YARN CPU counts task containers only and misses most of the custody layer's work.
- Mutual attestation is in none of these images; it was merged into `main` on 5 Nov 2026.
- Live-web runs on different days see different sites; compare runs within one series.

Analysis of these runs: `bench/results/README.md` on branch `subhiksha/source-provenance` of Heron-AI-Security/training-custody
(sections 1 to 7).

# ops/image: the image build of the fixed fleet (step F0)

This folder holds the sources of the **locked, measured image** of the fixed-fleet plan (milestone-plan.md section 10, steps F0.1 to F0.6). It replaces the rebuild kit `ops/rebuild/` at step F5. This is part 1: **F0.1** (kernel 6.17 is the default, so a plain reboot keeps RTMR3 extendable) and **F0.2** (the measurement runs as a unit at every boot, before any Hadoop daemon).

In plain words: at every boot the machine hashes a fixed list of its own files into the hardware register RTMR3, one line per item, before anything else starts, and keeps a log of those lines. A hardware quote then vouches for the register, and anyone can replay the log and get the same register. If the files are the same, the register is the same on every boot; if one file changed, the register changes. Nobody has to run a script by hand any more.

| File | What it is |
|---|---|
| `build/tc-image-prep.sh` | run on a builder or test VM: installs the pinned 6.17 kernel as the **default** (not a one-time boot), freezes automatic upgrades, and installs and enables the measurement unit; it never reboots |
| `rootfs/usr/local/lib/tc/tc-measure.sh` | the boot measurement: refuses to run unless RTMR3 is zero, measures the list in order, stops if a path is missing |
| `rootfs/usr/local/lib/tc/tc-extend.sh` | extends RTMR3 with the SHA-384 of a file or folder and logs it (the old `rtmr3-extend.sh` without `sudo`) |
| `rootfs/etc/tc/measured-paths.txt` | the list of measured paths: one line each, edit it to change what is measured |
| `rootfs/etc/systemd/system/tc-measure.service` | the unit, ordered before `multi-user.target` |
| `rootfs/etc/systemd/system/tc-placeholder.service` | TEST ONLY: stands in for the Hadoop daemons to prove the order |
| `test/f01-check.sh` | after each boot: 6.17 is the default and running, RTMR3 is not zero, the unit finished before the stand-in daemons, the log replays to RTMR3, a quote is bound to the log |
| `test/f01-compare.py` | compares two boots: the same files give the same RTMR3, one changed file changes only its event |
| `test/f01-drive.sh` | drives all of this on a disposable TDX VM from Cloud Shell |
| `test/f01-rehearse.sh` | the sandbox rehearsal with stand-ins (a fake register that extends like the hardware) and every fault made on purpose |

The scripts `attest/quote.sh`, `attest/measure/treehash.sh` and `attest/measure/rtmr3_replay.py` are reused unchanged and copied into the image by the prep script.

**What replaces what:** F0.1 replaces the one-time boot into 6.17 and the manual measurement of Milestone 1 (`ops/worker-kernel-prep.sh`, `attest/measure/`); F0.2 replaces the manual `measure-all.sh` runs and the re-measure after a reboot (step 4.8.2).

**What it does not show (limits).** The measurement unit is not itself measured by an earlier stage: someone who can write to the disk between boots could change `tc-measure.sh` to report the digests that they want. Closing that needs a read-only root with dm-verity or a measured initramfs; the mentor has been asked (limitations row 131), and until she answers the default is to measure the boot script, the units, `openssl` and `wg` and to state this limit. It is also tested on one disposable VM, with a stand-in for Hadoop; the real daemons, the keys and `fleet.tsv` come with steps F0.3 and F1.

## Step F0.3a: the software layer (JDK, Hadoop, the daemons)

On top of the preparation of F0.1 and F0.2, `build/tc-image-bake.sh` puts the software layer into the image: JDK 11, Hadoop 3.4.3 (checked against the checksum file of the Apache archive) in the root-owned `/opt/hadoop`, a service user `hadoop` that cannot log in (data in `/var/lib/hadoop`, logs in `/var/log/hadoop`), the plain configuration rendered from `rootfs/etc/tc/hadoop-props/*.props` and checked against them, one systemd unit per daemon (`rootfs/usr/local/lib/tc/units/`, in the measured folder, each requiring and following `tc-measure.service`), and the longer list `rootfs/etc/tc/measured-paths-f03a.txt` (the JDK, the Java settings, the CA fingerprints, Hadoop's code and configuration, besides the five items of F0.2). It is a single node that runs everything on itself, on the loopback address; the two-node run comes after the keys and the fleet list (F1, F2). `build/tc-image-clean.sh` then removes what belongs to the builder (machine id, ssh host keys, first-boot state, logs) so that its disk can become an image.

`test/f03-drive.sh` drives it from Cloud Shell: a builder VM, the bake, the image, and a test VM made from the image that `test/f03a-check.sh` checks after each boot. `test/f03a-rehearse.sh` is the rehearsal with stand-ins, and `test/f03-drive-rehearse.sh` tests the driver's handling of a restarted builder (its cleaned disk makes new ssh host keys, so the driver forgets the old remembered key of that instance).

What it does not show: the wrapper jar and the job (F0.3b), the crawl driver (F0.3c), two VMs from one image (F0.3d), the closing of the ports that cannot be bound to the loopback address, such as the shuffle port (F0.5), and the login paths that the image still has (F0.4: the guest agent and sshd stay for the test). The download measures the server's speed first and refuses one that would take more than 40 minutes (`HADOOP_URL_BASE` names a faster mirror, `HADOOP_ALLOW_SLOW=1` waits), shows its progress, resumes a partial file, and always takes the checksum file from the primary Apache archive, whichever server the tarball comes from. The Hadoop tarball is trusted through that checksum file; its hash is recorded in `/etc/tc/bake-versions.txt` so that it can be pinned.

## Step F0.3b: the job and the wrapper jar

After the bake, `build/tc-image-job.sh` puts the crawler's job and the wrapper jar into the image from **pinned inputs**, and removes the build tools again. Its inputs are a source archive made in Cloud Shell by `git archive` of a pinned commit (pinned by its SHA-256), and the teammate's patch at her commit `841c1d3` (pinned by its SHA-256, which starts with `61dbff2e`; it is not in this repository). It builds the two libraries of the crawler at pinned commits, unpacks the source, applies the patch, runs `ant runtime`, and builds `attested-hdfs.jar` from the job's own classes with `ops/attested/wrapper-jar.sh` (deterministic). The jar goes into Hadoop's library folder and the whole deploy folder (the job and the launcher scripts) into `/opt/tc/nutch`, both owned by root. The measured list grows to 11 events (`nutch-deploy`, last), every fingerprint is recorded in `/etc/tc/job-versions.txt`, and `ant`, `maven`, `git` and `patch` are purged with the build folder and the caches (`libcld2-0` stays: the job needs it at run time). It replaces the rebuild stages `deps`, `build` and `jar` of `ops/rebuild/node-wrapper.sh` for the image.

`test/f03b-check.sh` runs after each boot: the checks of F0.3a still pass; the baked job and jar are the recorded ones and owned by root; the wrapper jar is on Hadoop's classpath, its classes equal the job's, and it loads and initializes (`wrapper-jar.sh selftest`); Hadoop's Pi example runs on YARN; and a Nutch `inject` job from the baked job file runs on YARN and writes a crawl database to HDFS. `test/f03b-rehearse.sh` is the rehearsal with stand-ins. The driver has the stages `ship-source` and `job`, and `CHECK=f03b-check.sh` selects this check for the stage `check`.

What it does not show: the configuration stays plain, so the wrapper is on the classpath but nothing names its classes (it needs keys: F1 and F2); the crawl driver and the seeds are not baked yet (F0.3c); the crawler's identity URL in `conf/nutch-site.xml` is still the old fork's address and is baked into the job as it is.

## Step F0.3c: the crawl that runs by itself

`build/tc-image-crawl.sh` bakes the crawl driver `rootfs/usr/local/lib/tc/tc-crawl.sh`, its parameters `rootfs/etc/tc/crawl/params.env` and its seeds `rootfs/etc/tc/crawl/seeds.txt`, and the unit `tc-crawl.service` into the image, and extends the measured list to 13 events (`crawl-params` and `crawl-seeds`, last). The unit starts after the four Hadoop daemons, with no operator command; its skip condition (`ConditionPathExists=!/var/lib/tc-crawl/done`) is in `[Unit]` (rule 40), so a later boot does not crawl again. The driver reads its parameters as DATA (a line is `KEY=VALUE` with a plain value and nothing is executed), waits for HDFS and YARN, puts the seeds into HDFS, runs Nutch's own crawl script on the baked job with the parameters of the earlier runs (at most 10 fetch attempts over 3 rounds, on the two practice sites that obey `robots.txt`), checks that at least `MIN_FETCHED` urls are fetched and a segment exists, and writes the marker. `test/f03c-check.sh` only waits and reads: it checks the unit's start after the measurement and the daemons, its result, the marker, the crawl database and the segments in HDFS, and then runs the F0.3b check. It replaces the hand-run `ops/run-crawl.sh` and its typed parameters (legacy step 5.3.2) for the image.

What it does not show: the wrapper is still not in use (the crawl runs in plain mode until keys exist: F1 and F2), and the crawler's identity URL in the baked job is still the old fork's address until the configuration is changed and the job rebuilt.
